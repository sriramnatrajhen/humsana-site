Use cases

Actions that are hard to undo.

If an action can be reversed with a second action, a log is usually enough. These are the cases where it cannot. The boundary is the same in every one of them. What changes is the action, and the values that were bound when it was approved.

01

Money movement

Payments, releases, beneficiary changes and payout exceptions.

An exception waits in a queue after approval and is released later. The account in the queue row is not the account that was approved.

The refusal names the account field and both values.

02

Regulated communication

Notices, demands, filings and outbound batches.

The approved words and the recipient set both matter, and either can change between approval and send.

The refusal names the recipient set or the document that no longer matches.

03

Destructive actions

Deleting records, revoking access, closing accounts, destroying keys.

There is no second action that undoes them, so the check has to happen before the action rather than after it.

The refusal names the scope the action had grown to.

04

Access and provisioning

Creating an account, granting a role, issuing a credential.

The grant was approved for one person and arrives covering three.

The refusal names the principal or the scope that changed.

05

Records

Retention changes, bulk edits, exports of personal data.

The approved record set is not the set the action reaches.

The refusal names the record set that changed.

06

Commitments

Purchases, contracts, bookings and subscriptions.

The commitment outlives the session that made it, and the terms can move before it is signed or sent.

The refusal names the amount, the counterparty or the term that changed.

The action changes. The question does not.

Is this the action the principal authorized?

A grant answers it. The record proves the answer.

The same question holds whether the action moves money, sends a document, deletes a record, grants access or commits the company.

No grant. No execution.
