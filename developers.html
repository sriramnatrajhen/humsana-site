The integration is two calls and one rule.

The agent proposes an action. Humsana binds the authority to that exact action. Before the action runs, the executor checks it again.

No grant. No execution.

How a caller uses it.

01

Register the action class

The class names which values are bound, what consequence it carries, whether a human step is required, and which executor checks the decision. Registration is data, so the boundary holds no code path per action type.

02

Authorize the exact action

POST /v1/authorize/verify with the principal, the agent, the action name and its parameters. The answer is one of the six decisions, the action digest, the binding and the expiry.

03

Confirm where the consequence requires it

The approving human is authenticated by the principal's identity system. Humsana verifies what it is handed and signs the approval over the action digest, not over the request.

04

Check at the seam, immediately before acting

POST /v1/authorize/effectuate with the receipt and the action the executor is about to perform. An exact match proceeds. A material change is refused, and the changed field is returned.

05

Keep the record

The receipt carries what was claimed, established, authorized, presented, executed or refused, the policy version, both action digests, the approving identity and the timestamps.

One engine, any action the principal registers.

An action class is a registration: a name, the values that are bound, a consequence level, and the rules that apply at execution.

The two calls are identical for every class. Nothing in the boundary is written per action type, so adding a class does not add a code path.

Action classValues carried in the binding
payments.releaseamount, beneficiary, account, expiry, reference
filing.submitdocument, recipient set, deadline
access.revoketarget, scope
records.deleterecord set, retention class

Examples of registered classes. The binding is over the action, not over the class.

The vocabulary the boundary answers in.

Every response carries one of six decisions. Two of them are an authorization, and only those two can be executed on.

DecisionWhat it means
ALLOWThe action proceeds.
ALLOW_WITH_LIMITSThe action proceeds with the limits applied.
VERIFYSomething has to be verified before it proceeds.
HUMAN_CONFIRMAn authenticated human has to approve this exact action.
HOLDIt does not proceed until something changes.
DENYIt does not proceed.

The check has to be on the path that acts.

Humsana enforces at the execution seam controlled by the integrating party. The reference executor exists to demonstrate the seam and to be replaced by yours.

The boundary answers a question. The integrating party decides what happens when the answer is a refusal, and that decision is theirs to own.

What the service exposes.

EndpointPurpose
POST /v1/authorize/verifyPropose an action and receive a decision, a binding and an expiry.
POST /v1/authorize/effectuatePresent the action at execution and receive the decision and, where it moved, the field.
POST /v1/authorize/confirmRecord the confirmation, bound to the digest of the approved action.
POST /v1/authorize/challengeAsk for the challenge when an action requires a human decision.
POST /v1/authorize/confirm/requestRequest the confirmation step for an action that requires a person.
GET /v1/healthWhat the deployment is running: policy version, confirmation mode, router mode.
