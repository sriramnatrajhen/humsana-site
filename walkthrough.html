Five steps from your own command to a signed record.

You define an action class and send it to the live service. Change one field and read the refusal. Download the signed record and check it offline. Change one word of it and watch the check fail. Run an executor whose rail runs once.

The client and the verifier are the standard library only, so nothing is installed.

Open the sandbox Ask for the two files

Every command was run on 28 September 2026 against https://api.humsana.com, in one directory holding the boundary client and the offline verifier. The directory holds nothing else. Every line of output under a step is that run, copied unedited. Steps 1, 2 and 5 need the client. Steps 3 and 4 need the verifier and the two files it checks, the record and the public key. Neither is published for download yet, so ask if you want them.

Step 03the record, and the check

Download the record for that press and check it offline.

The sandbox issues a signed record for the action it presented, and serves the public key beside it.

The record route answers only in a session that has pressed, so curl keeps the cookie in jar.txt. This press changes the same field as step 2, and the code differs: the grant in this session covers a different action, so the service answers that rather than comparing field by field. In step 2 the caller establishes the binding itself, so there the comparison names the field and the rule.

$ curl -s -c jar.txt -o /dev/null -w 'GET  %{url_effective}  %{http_code}\n' https://api.humsana.com/sandbox/gregg/
GET  https://api.humsana.com/sandbox/gregg/  200

$ curl -s -b jar.txt -c jar.txt -o pressed.html -w 'POST %{url_effective}  %{http_code}\n' -d 'do=execute' -d 'amount_gbp=1800' -d 'beneficiary=Supplier X' -d 'account_four=9137' -d 'expiry=14:00' https://api.humsana.com/sandbox/gregg/

Step 05the seam, and the rail

Run an executor that asks before it acts.

The executor is the seam: it presents the action to the service before the rail call, and calls the rail only when the service says the two match.

rail() is the one function an integrator replaces, and here it is a stand-in that returns a transaction reference.

What these five steps do not establish.

Three limits apply to the run above, and it does not close them.

The actor is declared, not verified.

The public service runs with the agent register off. The identity on a request is what the caller says it is, not something a credential bound. The record from step 3 states this, and the client says the same at the end of its run. Nothing here shows that the caller is the agent it claims to be.

The rail is ours.

The rail in step 5 is a function inside our reference executor, and the sandbox page runs the sandbox app itself. Honoring a refusal is the integrating party's side of the seam, and a page cannot show their code deciding. The count shows what our executor did: nothing reached the rail.

The record is one party's account.

The acknowledgment block in the record from step 3 reads acknowledged_unsigned, and its signature is null: the executor recorded what it received but did not sign back. Until an executor counter-signs with its own key, the record is Humsana's account of the action and the decision, not a two-party record.

  • acknowledgment signaturenull, and the note says so
  • the record's own scopeit attests that Humsana issued the record and that it has not been altered since
