When AI acts on your behalf, authority has to travel with the action.

An agent can have permission to act and still execute an action nobody approved. Humsana binds authority to the action itself, checks that action again before execution, and refuses it when it no longer matches.

The executor already has rules. It does not have your authority.

The system that performs the action already decides a lot.

Whether the account exists and holds funds.

Whether the amount is inside a limit the system sets.

Whether the request is well formed, and whether the record is in a state that allows the change.

Those rules answer whether the action can run.

They do not answer whether someone authorized this action.

That authority sits somewhere else. An approval in a queue. A ticket. A message. A flag on a row.

Between the approval and the execution, the action can change.

The authority does not travel with the action. Humsana makes it travel.

One refusal, any action class.

The same check applies to every action class the principal registers. The refusal names the field that changed.

Two kinds of rule

A system enforces its own rules. A principal grants authority. The two are not the same, and only one of them is bound to the action.

What changes when authority travels with the action.

An approval covers one action and nothing else.

An approval can be spent once.

An agent can be given latitude, because the boundary holds it to the action rather than to the session.

The record answers the question later, in the same terms it was asked: what was authorized, what arrived, what was refused, and why.

The same two calls serve every action class the principal registers.
