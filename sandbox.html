Swan See it work
01Sandbox

One payout, one approval, one refusal.

A live deployment. Generated data, no real money, and the authorization service is the real one.

01

The hold

A payout is held because the beneficiary name does not match the account. That check belongs to the paying bank, and it already ran.

02

The repair

An agent reads the signed mandate and proposes a new destination account. Live mode is a real model call, and the claim is recorded as asserted.

03

The approval

A person approves the repaired instruction as it stands. The approval is single use, and it expires.

04

The release

The screen arrives holding the account on file, so the first press is a refusal. From there you can send the queue's copy, the version the agent read after the mandate was re-issued, an instruction whose name check now fails, an expired approval, or the instruction that was actually approved.

05

The record

Claimed, established, authorized, refused and executed, with the digest the grant was bound to. Downloadable.

One window, with the real exchange between the agent, the executor and the boundary underneath it, timestamped.

02The refusal

What it names.

refused: GRANT_DOES_NOT_COVER_THIS_ACTION field: payee_account authorized ... arrived ... rule MAY_NOT_CHANGE consumed: false

The field, both values and the rule, as a structure. Nothing is consumed, so the approved instruction can still be sent.

No approval

Refused before the rail. No grant found.

Past the window

Refused by the boundary's own expiry rule.

Replayed

Refused. A grant is spent once.

Straight to the rail

Refused for want of a grant. The rail is yours, and requiring one is the integration.
