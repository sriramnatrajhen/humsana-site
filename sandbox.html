Three runs, three outcomes.

The boundary authorizes the action, and it executes unchanged.

A higher-consequence action is held. A confirmation is answered by the reference confirmer described below, and the released grant executes once.

The action arrives with the amount raised from 1,800 to 2,400, and the boundary stops it.

The refusal names the field, both values and the rule that was broken.

There is nothing to fill in and nothing to configure. One button per run.

Each run ends with the record the boundary stored, and a link that checks it against the key this deployment publishes.

What the sandbox is.

No account and no login. Synthetic data only, and no money moves. A run keeps its own state for a short time, so a reload keeps it.

Each run ends with the authorization and the execution record the boundary stored. Open the run's finding to read them, and the proof link to have them checked. The verifier reports the signature, the record digest and the authorization link, and names the key it used.

Where the sandbox holds an action for a person, the confirmation is answered by humsana-ops-2026 (ops@humsana.com), a Humsana-operated reference confirmer. It demonstrates that the confirmation path works end to end. It is not a customer's approval.

The five-step run by command, with the record checked offline, is on the walkthrough.
