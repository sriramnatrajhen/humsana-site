01 Authorization

When AI acts on your behalf, authority has to travel with the action.

An agent can have permission to act and still execute an action nobody approved. Humsana binds authority to the action itself, checks that action again before execution, and refuses it when it no longer matches.

03 Why now

Agents are being handed the rails.

Payments networks and model providers spent 2025 building the paths that let an agent complete a purchase or a transfer. The checks that decide whether that action was authorized still live in queues, tickets and mailboxes.

Mastercard announced Agent Pay, technology for payments made by AI agents.Mastercard newsroom Source
29 September 2025
OpenAI and Stripe published the Agentic Commerce Protocol, an open standard for agent-initiated checkout.Agentic Commerce Protocol, released under Apache 2.0 Source
2025
Swift ran AI fraud detection across ten million test transactions with thirteen banks, and reported real time detection roughly doubled.Swift, press release Source

The check at the execution seam has to be cheap enough to sit on the path. Ours runs in single digit milliseconds, and the method and its limits are stated in full.

04 The gap

Permission answers a different question from authorization.

Permission
  • Can call the payment API
  • Has a credential
  • Access persists
  • Logs what happened
Authorization
  • Can make this payment
  • Has authority
  • The grant is bounded
  • Binds what was approved

The system that performs the action already decides whether the action can run. It checks the balance, the format, its own limits, screening and duplicates.

None of those rules answer whether the principal authorized this action. That authority sits in a queue, a ticket, a message or a flag on a row, and it can change before the action runs.

05 The refusal

An approved action can still be refused.

£1,800 to Supplier X was approved against account 4821. Before the release ran, the executor presented the same action with account 9137.

GRANT_DOES_NOT_COVER_THIS_ACTION · parameters.payee_account · authorized 4821 · presented 9137 · rule MAY_NOT_CHANGE · payment API not called

The authorization was not spent, so the approved action can still be executed as approved. The refusal names the field, both values and the rule.

The principal grants the authority. Humsana records it, binds it to the exact action and enforces it where the action would happen. Humsana verifies the authenticated identity or assertion the customer supplies, records who was authenticated and by which method, and binds that confirmation to the action.
