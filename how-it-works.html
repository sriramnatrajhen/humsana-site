01Mechanism

From authority to action.

What the caller must assert, and what the boundary refuses to infer from it.

02The request

An agent presents a claim, not a proof.

Who is asking

The agent identifies itself, and the organization or person it acts for. Humsana records the presentation as a claim and keeps it separate from anything it can establish.

What it wants to do

The action arrives as structured fields, not as a sentence. The boundary compares fields, so the executor and the boundary have to agree on the parameters of the action exactly.

What authority it claims

A mandate, a delegation, a policy reference, an approval from an upstream system. A delegation presented with a request is recorded as unverified today. Scope, revocation and expiry rules for a presented delegation are not enforced yet, and we do not imply otherwise.

What consequence it carries

The caller declares an action class. The declaration is recorded and can never lower what the class requires.

03Evidence

Five states, never blended.

Every fact the boundary carries an opinion about has one state, and the state travels with the fact into the record.

Measured

The boundary's own machinery produced this result.

Verified

An external check confirmed it, and the boundary knows which one.

Reported

A party said so, and the boundary repeats it as a report.

Unverified

It arrived as a claim and nothing supports it. This is the state of most of what an agent asserts.

Unknown

Nothing was established and nothing was claimed. Recorded as silence, not as consent.

Measured evidence outranks a caller's assertion, which outranks a caller's silence. A claim can make a decision stricter. It can never make one more permissive, and a declaration in the request never moves the verdict, the evidence grade or the action.

04Consequence

The action decides the floor.

The class sets a minimum, not a permission

Each action class carries a floor: how much evidence is required and whether an authenticated person has to confirm. The class comes from the action, so an agent cannot choose a lighter path for a heavier action by describing it differently.

Reversible actions stay cheap

A read, a draft, a search: no confirmation, and the check measured in single-digit milliseconds.

Irreversible actions floor at a person

Money movement, regulated communication and destructive actions floor at human confirmation by construction. The requirement comes from the consequence, not from the model's confidence.

05Confirmation

The approval is an act, not a flag.

Asked of an authenticated approver

The request names who is being asked and how the answer will be authenticated. That identity is what gets recorded against the approval.

Bound to the exact instruction

The approver sees the fields that will be bound, including the destination and the amount, and approves that instruction as it stands.

Spent once, and it expires

An approval covers one action, and it has a window. An approval that arrives after its window is refused by the boundary's own rule, not by the rail's.

What this is not

Humsana does not authenticate the approver. That belongs to the customer's identity system. The sandbox uses a reference confirmation adapter so a visitor can press the button, and it is not a customer identity system.

06The grant

Single use, exact action.

Every bound field is named

The grant carries the fields that may not change and their digests. A byte-level change to an artifact is a change to a field.

Sets may shrink, never grow

A recipient set, a record set, a resource list: a bound set may only shrink under its rule. Adding one recipient after approval is refused, and the refusal says which rule it failed.

A refusal names the field, both values and the rule

The response carries the field that moved, the value that was authorized, the value that arrived and the rule that was broken, as a structure rather than a sentence. An operator or a system can act on it without parsing prose.

07Execution

The check happens where the action happens.

The executor presents what it is about to do

Immediately before the send, the payment or the deletion, the executor presents the action it is holding together with the grant. The boundary answers in single-digit milliseconds, so the check is affordable on the hot path.

A moved field stops the action

If anything material changed since the approval, the call returns without releasing, the grant is not consumed, and the response says what moved.

Nothing is authorized twice

A second presentation of the same grant is refused, so a retry loop cannot release the same action twice.

The rail is the customer's, and it requires a grant

Humsana is not a payment rail and cannot make a customer's rail refuse an unsigned instruction. Making the rail require a grant is the integration, and the sandbox demonstrates the requirement rather than claiming the rail enforces it by itself.

08The record

The audit path is the executable path.

Recording is not a logging feature bolted beside the decision. Each step writes the state it produced: what was claimed, what was established, what was authorized, what executed, and what was refused, each with the reason. A refused action is not an error to be found in a log later, and an authorization cannot be rewritten after the fact.

Both outcomes are kept together, so a reviewer can see the control working and working by stopping something.

09The provider boundary

Models advise. Policy decides.

The decision is deterministic

The same request produces the same decision, and the deployment runs deterministic by default. No model sits in the authorization path.

A model can only raise

Where a language model is enabled as an optional provider, it can request a stricter outcome and nothing else. Its output has no field in which a decision could be carried, and a missing, empty or unreadable key file leaves the boundary running deterministically with no network call at all.

Bounded waits

The boundary waits for a provider only up to its own deadline, and records a timeout by name rather than treating a slow answer as an answer.

A provider can make a request stricter. It can never make one that policy refused go through.

10The calls

Four calls, and a refusal you can read.

POST /v1/authorize/verify decide whether this exact action may proceed POST /v1/authorize/confirm/request ask the authenticated approver POST /v1/authorize/confirm record that approval against that instruction POST /v1/authorize/effectuate release, only if the arriving action matches the grant

A refusal from the live sandbox reads like this, with the moving field named:

POST /v1/authorize/effectuate -> 200 authorized: false code: GRANT_DOES_NOT_COVER_THIS_ACTION matched: false consumed: false drift: payee_account authorized the account on the approved instruction arrived the account the executor was holding rule MAY_NOT_CHANGE

Field names and codes are the service's own, taken from a live call. The two account values are described rather than printed, because they are sandbox identifiers. The same shape appears on the Sandbox page.

Run it against a real service.

The sandbox is a live deployment. It holds a payout, has an agent repair it, asks one person to approve, and then refuses whatever instruction does not match that approval.
