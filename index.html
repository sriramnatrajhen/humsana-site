02The problem

Permission is not authorization.

A permission lets the agent call the API. It does not say this payment, to this account, for this amount, under this approval.

  • Destination changed. The approved account is not the account that arrives.
  • Artifact changed. The approved document is not the document being sent.
  • Scope changed. The action reaches more recipients than the approval covers.
  • Approval spent. The same approval is presented twice.
03How it works

From authority to action.

  • 01 Claim. The agent presents the action and the authority it claims.
  • 02 Establish. Humsana separates what it can prove from what was asserted.
  • 03 Confirm. Consequence decides whether a person approves. The approval binds to the exact fields.
  • 04 Enforce. The action is checked again before execution. A field that moved stops it.

An assertion stays an assertion. Repeating it does not make it evidence.

05Where it matters

Built for actions you cannot undo.

  • Money movement. Payments, payouts, beneficiary changes.
  • Regulated communication. Content, recipients and versions that must survive to execution.
  • Destructive actions. Deletions, revocations, key destruction.

Swan Voice is one evidence capability inside Humsana. It is live today.

06Boundary

What it is not.

Not a payment rail. Not an identity provider. Not KYC or monitoring. Not a model deciding what is authorized.
